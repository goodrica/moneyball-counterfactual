# Review: moneyball-counterfactual (2026-09-10)

Reviewer: Peggy_Sue. Repo state: **1 commit, scaffold only** — `README.md`,
`docs/PLAN.md`, `requirements.txt`, `.gitignore`. No `src/`, no tests, no
data, no site. Zero of Phases 0–6 implemented.

## Verdict

The research design is genuinely good — better than most sabermetrics blog
posts. It pre-registers hypotheses, learns old-school weights from the
historical market instead of asserting them, and builds in three real
controls (New-GM≈Actual, 1985–95 backtest, 100-seed variance). That part
needs no rework.

**But the plan cannot be executed as written.** Its data layer is broken in
three independent ways, all verified live today. Fix the data layer first or
Phase 0 dies on contact.

## Blocker 1 — the primary data source is GONE (404)

The plan and README both point at `chadwickbureau/baseballdatabank`.

```
https://api.github.com/repos/chadwickbureau/baseballdatabank  -> 404
raw .../master/core/Teams.csv                                 -> 404
raw .../master/contrib/Salaries.csv                           -> 404
```

The whole repo is gone, not just moved paths (tried master/main ×
core/contrib/root). Community mirrors survive, e.g.
`cbwinslow/baseballdatabank` (verified 200, 2985 team rows 1871–2021,
26428 salary rows). **A mirror is not a dependency you want under a
published study** — pin a specific commit SHA or vendor the CSVs.

## Blocker 2 — Lahman salaries STOP AT 2016 (fatal to the panel as designed)

Verified from the surviving mirror:

```
Salaries.csv: 26428 rows, 1985–2016   (last years: ...2013,2014,2015,2016)
1985–2002 training window: 14805 rows  OK — Phase 1 is fine
2010–2024 panel window:     5804 rows  ONLY 2010–2016 — 2017+ is EMPTY
```

Lahman discontinued salary collection after 2016. The plan's headline
("2015–2024 average win delta") and Phase 4 panel (2010–2024) **cannot be
computed** from Lahman. This is the single biggest finding of this review.

## Blocker 3 — `Teams.csv` has no payroll column

Phase 0/1 assume `Lahman Teams.csv` gives "Real W-L, RS, RA, **payroll** per
team-season." It does not:

```
Teams.csv: W/L/R/RA present = True
           payroll/salary columns = NONE
```

Team payroll must be **derived** by summing player salaries per team-season
(and that sum only works ≤2016, per Blocker 2). The optimizer's budget
constraint depends on this, so it needs its own task.

## Blocker 4 — FanGraphs scraping is 403 (WAR/wRC+/FIP source dead)

`pybaseball` 2.2.7 (the pinned version) is broken against FanGraphs:

```
pybaseball.batting_stats(2015) ->
  HTTPError: 'https://www.fangraphs.com/leaders-legacy.aspx' status 403
```

It still targets the retired `leaders-legacy.aspx` endpoint. The plan's
"free HTML tables, no API key" assumption no longer holds.

## The fix that solves 2, 3 and 4 at once

The plan's own documented fallback works — and does more than the plan
realized. Verified live:

```
pybaseball.bwar_bat(return_all=True)   -> 126,528 rows, years 1871–2026
pybaseball.bwar_pitch(return_all=True) ->  57,857 rows
columns include: WAR, WAR_def, WAR_off, WAR_rep, PA, G, team_ID, **salary**
salary coverage by year: 1990:883  2002:804  2015:817  2019:889
                         2023:858  2024:1152   (50,309 salaried rows total)
```

Baseball-Reference's WAR files carry **both WAR and salary through 2024+**,
from a stable static endpoint that returned 200 on the first try. So:

- **Salaries → bWAR files** (not Lahman) → panel extends past 2016, headline
  becomes computable again.
- **WAR → bWAR files** → no FanGraphs dependency for the modern model.
- **Team payroll → sum bWAR salaries by team_ID/year_ID** → Blocker 3 solved.
- **Lahman keeps** what it's still good at: Batting/Pitching counting stats
  (AVG, HR, RBI, R, SB, W, ERA, SV) for the OLD model, plus Teams W-L/RS/RA
  as ground truth. Those don't need post-2016 salary data.
- wRC+/FIP (FanGraphs-only) become **optional enrichment**, not a
  dependency. bWAR + Lahman rate stats can carry v1.

## Recommended next steps (in order)

1. **Re-baseline the data layer** (blocking, ~half a day): rewrite Phase 0
   around bWAR-for-salary/WAR + a SHA-pinned Lahman mirror for counting
   stats. Update PLAN.md's data table so it stops describing dead sources.
2. **Decide the panel window** with real coverage in hand: 2003–2024 is now
   possible via bWAR salaries. (Open question #1 in the plan is answerable
   now — this review is the answer.)
3. **Then Phase 1 exactly as written.** The valuation-engine design is
   sound; its Barry-Bonds validation gate is a good first real test.
4. **Add a data-contract test** before any modeling: assert row counts,
   year ranges, and that a known player's salary/WAR matches a hardcoded
   value. Every blocker above would have been caught by this test in Phase 0.
   The plan's "validation IS the science" instinct is right — it just needs
   to cover *upstream availability*, not only model behavior.
5. Housekeeping: add a LICENSE (repo has none — it's public and cites
   CC-BY-SA data), and note in README that Lahman salary ends 2016 so the
   next reader doesn't rediscover Blocker 2 the hard way.

## What NOT to change

- The three controls. They're the difference between this and a blog post.
- Pythagenpat-over-full-simulation for v1. Correct scope call.
- "New-GM ≈ Actual" as pipeline validation. Genuinely clever.
- The honest framing in Risks ("if OLD-GM loses by 1–2 wins, that IS the
  finding"). Keep that in the published site.

## Open question the plan didn't ask

Salary is *both* the OLD model's target variable and (summed) the
optimizer's budget constraint. With bWAR salaries replacing Lahman, both
come from the same file — so any systematic bias in that salary column hits
both arms. Worth one paragraph in Methodology, and a spot-check of a few
known contracts against Spotrac/Cot's.
